## 2026-07-29 - Server SDK hardcode route, không hỗ trợ custom path

- **Nơi xảy ra:** Server runtime `defineAADP()`/`handleRequest()`, từ `1.0.5`, vẫn còn ở `1.0.6`.
- **Triệu chứng:** URL sitemap index/sitemap/entity được publish trong manifest và path matcher của `handleRequest()` đều hardcode `basePath = /ai/v{version}`. Adapter muốn publish AADP document tại route khác phải tự viết lại toàn bộ runtime dù wire contract v1.0 không bắt buộc `/ai/v1.0/...`.
- **Nguyên nhân (root cause):** `runtime.ts` tự nối `basePath` vào cả URL builder (`entityUrl`/`sitemapUrl`/`sitemapIndexPath`) lẫn path matcher trong `handleRequest()`, không có lớp cấu hình route riêng — hai chỗ này luôn phải sửa đồng thời và không thể override độc lập với nhau.
- **Fix:** Thêm module route resolver riêng biên dịch một template (literal + `{type}`/`{id}` placeholder) thành cả URL builder và matcher, dùng chung cho route mặc định và route tùy chỉnh qua `AadpServerConfig.routes`. Validate và phát hiện collision (kể cả với `/.well-known/ai-manifest.json`) ngay tại `defineAADP()` time tại [src/server/routes.ts](src/server/routes.ts), tích hợp vào runtime tại [src/server/runtime.ts:272](src/server/runtime.ts#L272) và [src/server/runtime.ts:502](src/server/runtime.ts#L502), test tại [tests/server/routes.test.ts](tests/server/routes.test.ts) và [tests/server/runtime.test.ts:627](tests/server/runtime.test.ts#L627).

## 2026-07-29 - Literal route segment không canonicalize, matcher không nhận ra URL do chính resolver công bố

- **Nơi xảy ra:** `compileAadpRoutes()` trong route resolver mới thêm ở finding trên (`src/server/routes.ts`), phát hiện qua code review commit `ff48ea3`.
- **Triệu chứng:** Một `routes` config có literal chứa Unicode hoặc khoảng trắng (vd. `"/khám-phá/aadp"`, `"/custom maps/{type}"`) được `buildPath()` nối nguyên trạng vào URL công bố trong manifest/sitemap. Khi client dựng `Request`/`URL` từ chính URL đó, WHATWG URL parser chuẩn hóa pathname thành percent-encoded (`"/kh%C3%A1m-ph%C3%A1/aadp"`), nhưng `routes.match()` lại so khớp với regex dựng từ literal thô chưa encode nên trả `404 not_found` — server tự công bố một URL mà chính nó không phục vụ được. Ngoài ra, malformed percent-escape (vd. `"/maps/%ZZ-{type}"`) chỉ được kiểm tra khi cả segment là literal thuần, nên lọt qua `defineAADP()` nếu nằm chung segment với placeholder.
- **Nguyên nhân (root cause):** `compileTemplate()` giữ nguyên chuỗi literal do người dùng cấu hình, không canonicalize theo path percent-encode set mà `new URL()`/`Request` áp dụng, trong khi `buildPath()`, `segmentMatcher()` và collision detector đều đọc trực tiếp `token.value` — ba nơi cùng dùng một giá trị chưa chuẩn hóa nên không thể tự phát hiện sai lệch.
- **Fix:** Thêm `canonicalizePathLiteral()` implement đúng path percent-encode set (C0 control, `>0x7E`, space, `"`, `#`, `<`, `>`, `?`, backtick, `{`, `}`), áp dụng một lần cho mọi literal token tại compile time nên builder/matcher/collision detector luôn dùng chung representation canonical; đồng thời validate malformed percent-escape cho literal token trong mọi segment, không chỉ segment thuần literal, tại [src/server/routes.ts:112](src/server/routes.ts#L112). Test round-trip qua `Request`/`URL` thật (không tự dựng pathname) tại [tests/server/routes.test.ts](tests/server/routes.test.ts) và [tests/server/runtime.test.ts](tests/server/runtime.test.ts).

## 2026-08-01 - DNS-rebinding block bị chôn trong `TypeError: fetch failed` thay vì lộ ra `BlockedUrlError`

- **Nơi xảy ra:** `requestWithPolicy()` trong HTTP client dùng chung của reference client, validator CLI và conformance runner (`src/client/http.ts`), phát hiện qua AADP-109-005 (robustness regression corpus, `tests/client/dns-pin.test.ts`).
- **Triệu chứng:** Khi `pinnedLookup()` (`src/client/dns-pin.ts`) chặn một hostname resolve về địa chỉ private/loopback tại thời điểm connect (DNS rebinding — hostname trông "public" khi `UrlPolicy.check()` kiểm tra chuỗi, nhưng thực resolve về `127.0.0.1`), lỗi thực sự là `BlockedUrlError` ném từ callback của `dns.lookup`. Nhưng `fetch()` của undici bọc mọi lỗi ở giai đoạn connect thành `TypeError: "fetch failed"` với nguyên nhân thật nằm ở `error.cause`. Code cũ chỉ bắt `AbortError` rồi rethrow nguyên trạng, nên caller nhận `TypeError: fetch failed` thay vì `BlockedUrlError` — không nhất quán với đường kiểm tra string-level (`assertAllowed()`) vốn ném thẳng `BlockedUrlError`. Một consumer bắt riêng `BlockedUrlError` để phát hiện/báo cáo SSRF block sẽ bỏ sót hoàn toàn trường hợp DNS-rebinding.
- **Nguyên nhân (root cause):** `catch (err) { if (isAbortError(err)) {...}; throw err; }` không unwrap `error.cause` trước khi rethrow, trong khi `fetch()` luôn bọc lỗi network/connect thành `TypeError` một lớp.
- **Fix:** Thêm `unwrapBlockedUrlError()` kiểm tra `err.cause instanceof BlockedUrlError` và rethrow `cause` trực tiếp nếu đúng, áp dụng tại nhánh catch của vòng lặp request chính ở [src/client/http.ts:156](src/client/http.ts#L156) và [src/client/http.ts:312](src/client/http.ts#L312). Test end-to-end mock `node:dns.lookup` để giả lập DNS rebinding và assert `BlockedUrlError` lộ ra trực tiếp tại [tests/client/dns-pin.test.ts](tests/client/dns-pin.test.ts).

## 2026-08-01 - Canonical JSON crash với `RangeError` thô trên input lồng sâu bất thường

- **Nơi xảy ra:** `canonicalize()`/`checksumOf()` (`src/canonical-json/canonicalize.ts`, `src/canonical-json/checksum.ts`), gọi từ `assertOwnChecksum()` trong `src/client/validated-document.ts` để verify checksum của `sitemaps`/`items`/`data` lấy từ document do server (không tin cậy) trả về — phát hiện qua AADP-109-005.
- **Triệu chứng:** `serialize()` bên trong `canonicalize()` đệ quy thuần theo độ sâu object/array, không có giới hạn. Với input lồng khoảng ≥5000 cấp, hàm ném `RangeError: Maximum call stack size exceeded` — khác hẳn contract mà chính docstring của module công bố ("a validating canonicalizer... inputs outside the JSON/I-JSON value domain are rejected with a TypeError"). Vì `checksumOf()` chạy trên field do server cung cấp (entity `data`, sitemap `items`, sitemap-index `sitemaps`) mà client không giới hạn độ sâu ở bước nào khác, một server (hoặc man-in-the-middle) có thể gửi document lồng sâu bất thường để khiến client ném lỗi runtime thô thay vì lỗi loại rõ ràng, dễ đoán.
- **Nguyên nhân (root cause):** `serialize()` không có bất kỳ giới hạn hoặc bắt lỗi nào quanh đệ quy; `RangeError` từ stack overflow lọt thẳng ra ngoài `canonicalize()` thay vì được chuẩn hóa như mọi input ngoài domain khác của module (lone surrogate, `NaN`/`Infinity`, sparse array, `undefined`...).
- **Fix:** Bọc lời gọi `serialize()` trong `canonicalize()` bằng try/catch, chuyển `RangeError` thành `TypeError` rõ ràng ("Canonical JSON input is too deeply nested to serialize") tại [src/canonical-json/canonicalize.ts:13](src/canonical-json/canonicalize.ts#L13). Không đổi thuật toán serialize (vẫn đệ quy) — chỉ chuẩn hóa loại lỗi khi vượt giới hạn stack thực tế của runtime, nhất quán với phần còn lại của module. Test tại [tests/schema/checksum.test.ts](tests/schema/checksum.test.ts): 1000 cấp lồng nhau vẫn serialize bình thường, 1.000.000 cấp ném `TypeError` chứ không phải `RangeError`.

## 2026-08-01 - `aadp-conformance` CLI: lỗi parse argv trả exit code 1, đụng độ với "1 = check thất bại"

- **Nơi xảy ra:** `aadp-conformance` CLI (`src/conformance/cli.ts`), phát hiện qua AADP-109-005 khi viết test cho numeric option edge case ở tầng CLI thật (không chỉ tầng thư viện `runConformance`).
- **Triệu chứng:** CLI tự công bố exit code contract rõ ràng trong `--help` (0 conformant, 1 có check fail, 2 run không thực hiện được, 3 sai version, 4 run dở dang). Nhưng mọi lỗi parse argv của Commander (thiếu `<base-url>`, flag không tồn tại, `--timeout abc`/`NaN`/`Infinity`/số thập phân) đều thoát bằng `process.exit(1)` mặc định của Commander — cùng exit code với "ít nhất một check thất bại". - **Nguyên nhân (root cause):** CLI không cấu hình `program.exitOverride()`, nên `Command._exit()` gọi thẳng `process.exit(err.exitCode)` mặc định (luôn là `1` cho lỗi parse argv của Commander) — không đi qua nhánh `runConformance`/`InvalidConformanceOptionsError` (vốn map đúng vào exit `2`).

Thêm `.catch(() => {})` sau `program.parseAsync()` vì exitOverride khiến lỗi bị rethrow ra ngoài promise, tại [src/conformance/cli.ts:81](src/conformance/cli.ts#L81) và cuối file. Test tại [tests/package/conformance-cli.test.ts](tests/package/conformance-cli.test.ts): thiếu argument, flag lạ, và toàn bộ numeric option (`--timeout`, `--max-redirects`, `--max-response-bytes`, `--max-entities`, `--max-sitemaps`, `--deadline`) với giá trị `NaN`/`Infinity`/âm/thập phân đều exit `2`, không bao giờ `1` hay in `RESULT: PASSED`.

- **Nơi xảy ra:** `aadp-conformance` CLI (`src/conformance/cli.ts`), phát hiện qua code review commit `2ef60a7` (review `.claude/review/review-20260801-174557.md`, finding P1) — chính là regression side-effect của fix exit-code ở finding ngay phía trên.

Test tại [tests/package/conformance-cli.test.ts](tests/package/conformance-cli.test.ts): `--header malformed` phải exit `2`, in đúng message, và `stdout` phải rỗng (không phải một run "thành công" ma).

- **Nơi xảy ra:** `.github/workflows/ci.yml`, job `engines-floor-smoke` mới thêm để verify đúng `engines.node` floor (`20.18.1`) trên runner sạch — phát hiện qua code review commit `01c55b2` (review `.claude/review/review-20260801-181611.md`, finding P1).

- **Nguyên nhân (root cause):** `npm pack --pack-destination <dir>` giả định `<dir>` đã tồn tại; không tự `mkdir -p`. Tái hiện local: `rm -rf /tmp/x && npm pack --pack-destination /tmp/x` → ENOENT; `mkdir -p /tmp/x` trước thì pass.
- **Fix:** Thêm bước `mkdir -p /tmp/floor-pack` ngay trước `npm pack --pack-destination /tmp/floor-pack`, tại [.github/workflows/ci.yml:59](.github/workflows/ci.yml#L59).
- **Rule:** Không giả định lệnh ghi file (`npm pack --pack-destination`, `tar -xzf` vào thư mục con, v.v.) tự tạo parent directory. Verify bằng cách tái hiện local với destination thật sự chưa tồn tại, không chỉ đọc doc/help text của lệnh.
